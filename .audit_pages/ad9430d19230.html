About the JWT Decoder

The JWT Decoder splits a JSON Web Token into its three parts and shows the header and payload as readable JSON, with the timestamps in the claims converted to actual dates. It is the fastest way to answer the two questions that come up whenever a token misbehaves: which algorithm signed it, and when does it expire. The decoder is deliberately explicit about one thing, because it is the source of a great many security bugs: decoding a token is not verifying it. Anyone can read and modify the payload of a JWT, so the contents are only trustworthy after the signature has been checked against the issuer's key.

Where people use the JWT Decoder

  • Diagnosing an unexpected 401 by checking exp and aud.
  • Confirming which algorithm an identity provider actually signed with.
  • Reading custom claims such as roles or tenant IDs during integration work.
  • Teaching someone why a JWT payload is not a secret store.

How to use the JWT Decoder

  1. 1

    Paste the token

    Copy the whole string, including all three dot-separated parts. Tokens copied from a browser header often pick up a leading Bearer prefix, which the decoder strips automatically.

  2. 2

    Read the header

    The alg field names the signing algorithm and typ should be JWT. An alg of none means the token is unsigned, which no production service should accept.

  3. 3

    Read the claims

    Look at iss and aud to confirm the token was meant for your service, sub to see who it represents, and exp to see when it stops being valid.

  4. 4

    Check the timestamps

    exp, iat and nbf are seconds since the Unix epoch, not milliseconds. The decoder shows both the raw number and the readable date so you can tell a genuine expiry from an off-by-a-thousand error.

  5. 5

    Verify, then trust

    Use your library to validate the signature and the claims before acting on anything you read here.

Tips and best practices

  • Never put anything sensitive in a JWT payload; it is readable by design.
  • Reject the none algorithm explicitly rather than relying on a library default.
  • Keep access token lifetimes short and refresh them, rather than issuing long-lived tokens with broad claims.

Frequently asked questions

Does decoding a token prove it is genuine?

No, and this is the important point. Base64url is an encoding, not encryption. The payload is readable and editable by anyone holding the token. Only the signature check, performed with the issuer's key, establishes that the claims have not been altered.

Where is the signature checked?

On the server, using the shared secret for HMAC algorithms or the public key for RSA and ECDSA. A browser has no business verifying a token it is also allowed to read, because it cannot keep a key secret.

Why does my token have only two parts?

Because it is not a signed JWT. Some libraries issue unsecured tokens with an empty signature, which still leaves three segments separated by two dots. Two segments usually means the token was truncated when copied.

What is the difference between base64 and base64url?

Standard base64 uses plus and slash, which are unsafe in URLs and headers. Base64url substitutes minus and underscore and drops the padding equals signs. A token that fails to decode is often one that was passed through a URL without this conversion.

Why is exp in the past on a token I just received?

Either the issuer set a very short lifetime, or the value is in milliseconds when the consumer expects seconds. A token with exp around 1.7 billion is in seconds; a value with thirteen digits is in milliseconds.

Is it safe to paste a real token here?

The decoding happens entirely in your browser and nothing is transmitted, so the technical risk is nil. The practical advice still stands: treat any token as a live credential, and prefer a test token over one belonging to a real user.
