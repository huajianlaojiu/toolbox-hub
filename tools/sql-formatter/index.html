About the SQL Formatter

The SQL Formatter rewrites a query with consistent keyword casing, one clause per line and indented subqueries, which makes the structure of a long statement visible at a glance. That matters most when a query has several joins and a nested aggregate, because unformatted SQL hides the join conditions in a wall of text and mistakes there produce wrong results rather than errors. Formatting only touches whitespace and keyword case, so the query means exactly the same thing afterwards, but it does not validate the SQL: a query with a misspelled column name will still format perfectly.

Where people use the SQL Formatter

  • Making a query pasted from an application log readable before debugging it.
  • Standardising formatting across a team so reviews focus on logic rather than whitespace.
  • Expanding a one-line ORM-generated query to see which joins it actually produced.
  • Preparing SQL for documentation or a ticket.

How to use the SQL Formatter

  1. 1

    Paste the query

    Any length works. Minified output from an ORM or a log line with escaped newlines is the usual input.

  2. 2

    Choose a dialect

    Dialects differ in identifier quoting, string concatenation and pagination syntax. Picking the right one keeps backticks or double quotes intact instead of escaping them.

  3. 3

    Pick a keyword case

    Uppercase keywords such as SELECT and WHERE with lowercase identifiers is the common convention, and it separates language from your own names at a glance.

  4. 4

    Format, then read the structure

    Each clause should start on its own line. If a join condition appears in the wrong place after formatting, it was in the wrong place before.

Tips and best practices

  • Format first, then read the join order; a misplaced ON clause is much easier to see with one clause per line.
  • Keep one statement per block so the formatted output is not ambiguous.
  • Do not format inside a migration file that has already been applied; the diff will be noise.

Frequently asked questions

Does formatting validate my SQL?

No. It is a lexical transformation that understands keywords and quoting rules but does not know your schema. Run the query against a database or a linter to check it is valid.

Will formatting change what the query does?

It should not, because only whitespace outside string literals and the case of keywords are changed. Identifier case is significant in some databases, which is why the dialect setting matters.

Why did my string literal get mangled?

Usually an unbalanced quote. If a single quote inside a string is not escaped by doubling it, the formatter treats the rest of the query as part of the literal.

Which dialect should I choose?

The one the query will actually run on. MySQL uses backticks for identifiers, PostgreSQL and SQL Server use double quotes and brackets respectively, and pagination syntax differs between LIMIT and TOP.

Can I use this to make a query compact instead?

Yes, the reverse direction exists. When a query is going into a log line or a URL, minifying removes the newlines without changing the semantics.
